# Decision Log — Metableton Ecole PRD

## 2026-06-09 — PRD Creation Session

### Mode & Approach
- **Decision:** Fast path chosen for PRD creation
- **Rationale:** User provided detailed requirements upfront; brief, addendum, and decision log already available as source material

### Enrollment Flow
- **Decision:** Moderated enrollment request flow (not self-serve, not invitation-only)
- **Flow:** Student requests enrollment → system creates pending enrollment → teacher/admin approves or rejects → approved students see Classroom link
- **Rationale:** User explicitly specified this as an MVP product decision. Balances openness (any student can express interest) with control (teacher vets who joins their Classroom)

### Admin Bootstrap
- **Decision:** First Google user to sign in is automatically assigned `admin` role; all subsequent users default to `student`
- **Rationale:** User confirmed the bootstrap assumption. Eliminates the chicken-and-egg problem of role assignment

### Google Classroom Integration Depth
- **Decision:** MVP uses Classroom API for validation only (GET /v1/courses/{id}); does not create Classrooms, manage rosters, or sync enrollments programmatically
- **Rationale:** Keeps MVP scope tight; avoids consumer-account restrictions (@gmail.com can't create ACTIVE courses); teacher manages Classroom roster manually
- **Marked as:** [ASSUMPTION] #4 in the PRD

### Admin Course Editing
- **Decision:** Admin can edit any course in MVP (not just view)
- **Rationale:** Prevents orphaned-course problem if a teacher leaves; marked as potentially contentious
- **Marked as:** [ASSUMPTION] #5 in the PRD, surfaced as OQ-1

### Meet Link Display
- **Decision:** MVP does not extract and display Meet links inline on the dashboard; students click through to Classroom
- **Rationale:** Simpler implementation; Google Classroom already surfaces the Meet link prominently
- **Marked as:** [ASSUMPTION] #6 in the PRD

### Notifications
- **Decision:** No notification system in MVP (email or in-app) for enrollment status changes
- **Rationale:** Acceptable at 5-student scale; students check dashboard manually
- **Flagged:** [NOTE FOR PM] in §7.2 — most load-bearing deferral; consider v1 inclusion if manual checking creates poor UX

### Rejected Enrollment Retry
- **Decision:** Deferred to OQ-3; recommend retryable (re-request resets to pending)
- **Rationale:** Not user-specified; surfaced as open question for resolution before implementation

### Notification of enrollment approval
- **Decision:** Not specified; students must manually check dashboard. Identified as risk R-4.
- **Rationale:** Acceptable at 5-student MVP scale.
